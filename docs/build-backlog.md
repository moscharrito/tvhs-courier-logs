| 4.8 | Cold-start burst | 0.5 | Done, and the premise was wrong, which is the finding. This row said the fix was an index review plus a warm-up at boot. Measured: the first manifest read a freshly booted process serves takes ~18 ms, later ones ~6 ms, and twelve at once cold take 55 ms in total. A warm-up buys 18 ms once and was not written. The two-second reads in 4.1 are the import: the manifest read and the 300-row import take the same time to within a few ms in every run, because one process holds one connection and the import is ~900 statements the reads are interleaved with. The manifest is not slow, it is waiting. What the investigation did turn up is a real latent defect: with no statistics SQLite chose the unique index on (project_id, order_id) for that query, used only its leading column, and walked every stop in the PROJECT to return one courier's twenty. Fixed by an index on (project_id, run_id, sequence) so the planner cannot get it wrong, rather than by ANALYZE which only usually corrects it; PRAGMA optimize also runs at boot and daily for everything else. test/query-plans.test.mjs asserts the plan itself, because a missing index does not fail a test, it makes one slower. | 6.1 | Driver applications | 1 | **Done, DoorDash model.** `POST /api/driver-applications` is public and throttled and creates **an account with the password the applicant chose**, plus the application. They can sign in from that moment and see nothing, because the account belongs to no project. The first cut had an administrator typing a username and a temporary password per driver, which is fine for two couriers, wrong for two hundred, and puts a password in an email. So the property moved, deliberately: it is no longer "an applicant has no account", it is **no membership, no data**, and the access matrix now carries an `applicant` principal so every row in it also answers "can an unvetted stranger reach this". Approval grants the membership; rejection disables the account.
